# 08. 실수 사례와 교훈

실제 신청서 작업에서 사용자에게 지적받았거나 검증 중 발견한 실수를 모았다. 다음 회사에서는 처음부터 피한다. 각 사례는 「무슨 일 → 왜 → 예방」 순서다.

---

## A. 사용자, 회사 작업을 훼손한 실수 (가장 심각)

| # | 무슨 일 | 왜 | 예방 |
|---|---|---|---|
| A1 | md에서 docx를 다시 만들어 사용자가 지운 표식, 문구가 되살아남 | 사용자가 docx를 고치기 시작했는데 md를 원본으로 계속 씀 | docx를 고치기 시작하면 docx가 원본(06 문서). 전환 시점을 사용자와 확인 |
| A2 | 사용자가 고친 요청 리스트를 생성 스크립트로 다시 만들어 덮어씀(위험) | 「다시 만들면 깔끔하다」는 생각 | 사람이 고친 파일은 새 줄만 덧붙임 |
| A3 | 장 제목 스타일 id가 바뀐 것을 몰라 문서 전체를 한 장으로 인식, 다른 팀 장의 메모까지 지운 결과물이 나옴 | 장 구분 기준을 한 가지 스타일 id로만 둠 | 여러 id 허용 + 작업 전 Ⅰ~Ⅸ 다 잡혔는지 확인. 결과 검증에서 다른 장 XML 동일 확인 |
| A4 | 문서 전체에 서식 스크립트를 돌려 다른 팀 장까지 바뀔 뻔함 | 편해서 전체 적용 | 고친 표, 문단에만 적용 |

## B. 지시를 잘못 읽은 실수

| # | 무슨 일 | 왜 | 예방 |
|---|---|---|---|
| B1 | 「잘 보이게 해 줘」에 열을 넓히면서 글자를 8pt로 줄임 | 폭을 맞추려고 글자부터 줄임 | 글자 크기는 최후의 수단(03 문서) |
| B2 | 주식 종류를 지시대로 「보통주」로 통일했다가, 다음 판에서 「우선주와 보통주 구분이 왜 없냐」는 지적 | 지시 문장만 보고 표의 목적을 이해하지 못함 | 취득 당시 종류를 쓰고 머리글에 현재 기준(보통주)을 밝히는 식으로 두 요구를 함께 만족 |
| B3 | 「비고/재무상당액 좁히면 되잖아」를 그 두 열만 줄여 약력이 거의 안 넓어짐 | 지시를 문자 그대로만 수행 | 지시의 목적(약력을 잘 보이게)을 달성했는지 숫자로 확인, 모자라면 다른 열도 줄이고 보고 |
| B4 | 「회사가 칠한 색은 그대로」를 글자색까지 적용해 빨간 글자가 남음 → 「빨간색은 왜 있어」 | 형광펜과 글자색을 구분하지 않음 | 색 처리 기준을 처음에 사용자와 확정(06 문서 4절) |
| B5 | 「이건 없었어?」 질문에 자료를 찾아보니 회사 변동표에 값이 있었지만 액면가 자리표시였음 | 원천 값의 성격을 확인하지 않으면 잘못 채울 뻔함 | 같은 표의 다른 회신값과 대조해 신뢰도 판단(02, 05 문서) |

## C. 스크립트, 검증 실수

| # | 무슨 일 | 왜 | 예방 |
|---|---|---|---|
| C1 | 칸을 두 줄로 나눌 때 첫 줄 글자가 둘째 줄에 다시 붙음(「유상증자 / 유상증자(출자전환)」) | 첫 문단을 복사해 둘째 문단을 만들면서 이미 넣은 글자까지 복사 | 빈 틀(문단 서식, 글자 서식만)에서 새 문단을 만들고, 결과를 칸 단위로 출력해 확인 |
| C2 | 두 문단에 걸친 @ 지시의 뒷부분이 표 머리글에 남음 | 「@부터 문단 끝까지」만 지움 | @부터 칸 끝까지 지우고 잔여 확인 |
| C3 | 문단을 합치면서 그 안의 메모 표시가 사라져 본문 연결 없는 메모가 남음 | 메모 정리를 문단 편집 뒤 본문 기준으로만 함 | 마지막에 연결 없는 메모까지 정리 |
| C4 | 셀 내용을 지운 뒤 다시 쓰면서 글자 크기 정보가 빠져 한 칸만 글씨가 다름 | 첫 런의 서식을 복사하는데 이미 런을 지운 뒤였음 | 지우기 전에 서식을 복사해 두고, 결과에서 표 안 글자 크기 통일 확인 |
| C5 | 반올림 1 차이(744,544 vs 744,545) | 파이썬 round는 은행가 반올림 | Decimal ROUND_HALF_UP |
| C6 | 「29.25」를 날짜로, 「2024.03」을 숫자로 판정해 정렬이 틀림 | 판정 규칙이 느슨함 | 날짜는 4자리 연도 또는 YY.MM.DD만, 판정 순서는 날짜 → 숫자 |
| C7 | 반복 치환에서 새 글이 옛 글을 포함해 무한 반복 | 「바뀔 때까지 반복」 구조 | 새 글이 옛 글을 포함하면 한 번만 치환 |
| C8 | 열 폭을 처음 계산했을 때 오히려 글자가 더 작아짐 | 모든 짧은 글을 한 줄에 넣으려 해 최소폭이 커짐 | 숫자, 날짜만 한 줄, 글은 의미 단위 줄바꿈 허용, 원래보다 작아지면 손대지 않음 |
| C9 | 사용자가 정한 열 폭을 그대로 쓰니 숫자가 중간에서 잘림 | 사람 눈 조정은 실제 글자 폭과 다를 수 있음 | 글꼴로 실제 폭을 재 숫자가 넘치는 열만 넓히고 그 사실을 보고 |

## D. 사실, 근거 실수

| # | 무슨 일 | 왜 | 예방 |
|---|---|---|---|
| D1 | 요청 문구에 「○○일 갱신」을 넣었다가 「확인 안 됨」이라며 지웠는데, 실제로는 다른 명세서에 있던 사실이었음 | 추출 캐시 전체를 검색하지 않고 판단 | 사실을 넣거나 지우기 전에 추출 캐시 전체 검색 |
| D2 | 계약서 스캔이 엑셀의 숨김 시트에 그림으로 들어 있었음 | 엑셀은 보이는 시트만 봄 | 숨김 시트, 그림, 도형까지 확인(02 문서) |
| D3 | 계약서 서명일이 계약기간과 맞지 않음(오기 추정) | 원문을 그대로 옮기면 틀린 값 | 합리적 값으로 쓰되 메모와 요청으로 확인 |
| D4 | 기관 성격 분류(벤처금융 / 전문투자자) 판단 | 기관이 두 지위를 함께 가짐 | 거래소 실무 해설서의 기준을 찾아 근거와 함께 적용 |
| D5 | 업무 성격을 추정해 적음(선급금 내역 등) | 계정과 거래처로 추정 | 추정이면 「추정」이라고 보고하고 확인 요청 |

## E. 소통 실수

## 다음 회사에서 처음부터 할 것(요약)
1. docx 전환 시점, 색 표시 처리, 다른 팀 담당 장을 첫 주에 사용자와 정한다.
2. 장 구분, 메모 연결, 다른 장 불변을 매 판 자동으로 확인한다.
3. 바꾼 칸은 매 판 하나하나 전후 대조한다.
4. 글자 크기는 줄이지 않는다는 전제로 표를 설계한다.
5. 회사 회신은 같은 자료 안의 다른 값과 대조한 뒤 쓴다.
