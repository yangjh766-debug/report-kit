# 06. docx 피드백 루프 (사용자, 회사가 docx를 직접 고치기 시작한 뒤)

신청서 docx를 사용자와 회사가 직접 고치기 시작하면, 그 docx가 원본이 된다. 이 문서는 그 뒤에 판을 거듭하는 방법이다. 핵심은 **지시받은 곳만 고치고 나머지는 한 글자도 바꾸지 않는 것**이다.

---

## 1. 판 하나를 만드는 순서

```mermaid
flowchart TD
    A[사용자, 회사가 고친 docx 받음] --> B[날짜 붙여 이력 폴더에 보관]
    B --> C[이전 판과 비교<br/>장별 바뀐 줄, 새 메모, @ 지시]
    C --> D[@ 지시, 회신, 메모를 할 일 목록으로]
    D --> E[고칠 것만 고치는 스크립트 또는 수작업<br/>원본은 보관본에서 읽음]
    E --> F[칸 단위 전후 대조<br/>다른 장 XML 동일, 메모 수, 색]
    F -->|의도 밖 변화| E
    F --> G[다음 판 저장 vDraft-N+1]
    G --> H[기록: 검토기록, 폴더변경기록]
    H --> I[사용자에게 보고<br/>바꾼 것, 남긴 것, 확인 필요]
```

```
[고친 docx 받음] → [보관] → [이전 판과 비교] → [할 일 목록]
   → [고칠 곳만 수정] → [칸 단위 대조] ─(의도 밖 변화)→ 다시 수정
   → [다음 판 저장] → [기록] → [보고]
```

## 2. 받은 파일 다루기
1. **시작점은 항상 사용자가 마지막으로 고친 docx.** md에서 다시 만들지 않는다(사용자가 지운 것이 되살아나고, 고친 서식이 사라진다).
2. 받은 파일은 곧바로 `검토/docx_이력/<무엇>_<누가>_<MMDD_HHMM>.docx`로 복사해 두고, 스크립트는 이 보관본을 읽는다. 사용자가 Word로 열어 둔 파일을 직접 고치지 않는다.
3. 결과는 새 이름으로 저장한다(vDraft-N → vDraft-N+1). 사용자가 쓰는 이름 체계가 있으면 따른다.
4. 파일 수정 시각을 보고 사용자가 그 사이 고쳤는지 확인한다. 고쳤으면 그 판을 새 시작점으로 삼는다.
5. Word 잠금 파일(`~$…`)이 있으면 열려 있는 것이다. 덮어쓰지 않는다. **사용자가 Word로 연 채로 내가 파일을 고치면, 사용자가 Word에서 저장하는 순간 내 수정이 통째로 덮인다**(Word 저장은 메모 번호도 다시 매긴다). 열려 있으면 먼저 「저장하지 말고 닫아 달라, 고친 게 있으면 다른 이름으로 저장해 달라」고 요청한다.
6. 고친 뒤에는 `docProps/core.xml`의 마지막 저장자(lastModifiedBy)와 저장 시각(modified)으로 그 사이 사용자가 저장했는지 확인한다. 저장됐으면 열린 시점 판과 저장본을 글 단위로 비교해 사용자 수정을 살린 채 내 작업을 다시 적용한다. 메모 검증은 번호가 아니라 작성자, 문구, 개수로 한다.
7. **「최신」이라고 받은 판을 바로 덮지 않는다.** 다른 팀이 옛 판에 자기 장만 고친 판일 수 있다. 보관본들과 장별 글, 메모를 비교해 바탕 판을 찾고, 새로 바뀐 장만 장 단위로 옮긴다. 「어느 장이 새것인지」 보여 주고 합칠 범위를 확인받는다.
8. 회사가 보낸 파일은 이름이 옛 판 이름이어도 저장일이 새로울 수 있다. 마지막 저장자, 저장일을 보고 직전 사본과 비교해 새로 바뀐 칸만 정보로 옮긴다. 회사 파일 전체로 덮지 않는다.
9. 사용자가 Finder에서 파일 이름을 바꿨으면 그 이름을 따른다. 새로 만들기 전에 이름이 바뀌었는지 확인한다(맥에서 바꾼 이름은 NFD라 비교할 때 NFC로 정규화).

## 3. @ 지시 처리
- 사용자는 본문이나 표 칸에 「@지시」를 적는다. 지시를 수행하고 @ 문구는 지운다.
- **@ 문구가 두 문단 이상에 걸칠 수 있다.** @부터 그 칸(또는 문단 묶음) 끝까지 지우고, 지운 뒤 「@」가 0건인지, 지시 문구의 뒷부분이 남지 않았는지 확인한다.
- 지시가 모호하면 사용자가 직접 고친 예시를 본다. 예: 한 칸을 직접 두 줄로 나누고 「@이런식」이라고 쓰면, 같은 표의 비슷한 칸도 그렇게 하라는 뜻이다.
- 지시가 「여기는」이라도 같은 구조의 표가 여러 개면(예: 연도별 임원 표) 같이 맞추고 그렇게 했다고 보고한다.
- 「요청자료에 있나?」 같은 질문형 @는 요청 리스트를 확인해 답하고, 없으면 요청 한 줄을 추가한다.

## 4. 사용자, 회사 수정의 보존
- 사용자가 지운 것, 줄인 것, 직접 고친 문구는 그대로 둔다.
- **색 표시:** 회사는 새 입력에 빨간 글자나 빨강, 노랑 형광펜을 칠해 두는 경우가 많다. 기본은 그대로 두되, 사용자가 원하지 않으면 다음처럼 정리한다(작업 전에 한 번 확인).
  - 형광펜은 모두 빼고, 채워야 할 대기 표식(`##`, `[확인 필요: …]`, `[작성 대기: …]`)만 노란색.
  - 회사 입력의 빨간 글자는 검은색. 단, 안내 메모(「확인 필요」 같은 지시문, 주관사 몫 안내)는 색을 남겨 본문과 구분.
  - 회사 입력 글을 다시 쓸 때(줄바꿈 정리 등) 첫 글자의 서식을 복사하면 회사의 빨간색이 따라온다. 의도와 맞는지 확인한다.
- **다른 팀이 맡은 장**(예: 사업의 내용)은 내용, 서식, 메모, 색까지 손대지 않는다. 결과에서 그 장이 원본과 XML 단위로 같은지 확인한다.
- 문서 전체에 서식 스크립트(정렬, 줄간격, 글자 크기)를 돌리지 않는다. 고친 표나 문단에만 적용한다.

## 5. 메모(Word 메모)
- 「완료」, 「기입 완료」, 「수정했습니다」 같은 회신 메모는 내용을 확인한 뒤 지운다.
- 질문, 확인 요청(「확인 부탁드립니다」), 아직 답하지 않은 것은 남긴다.
- 우리가 다는 메모는 사용자 판단이 필요한 곳에만 한다. 예: 문서 원문과 다르게 적은 곳의 근거와 확인 요청. 메모 내용은 요청 리스트에도 한 줄로 남긴다(메모를 지워도 놓치지 않게).
- 메모를 지울 때는 본문의 시작, 끝 표시, 참조 런, 메모 본체와 부속 파일(commentsExtended, commentsIds, commentsExtensible)을 함께 지운다. 문단을 지우거나 합치면 그 안의 메모 표시도 사라지므로, 마지막에 **본문에 연결이 없는 메모가 남지 않았는지** 확인한다.
- 다른 팀 장의 메모는 지우지 않는다.

## 6. 장 구분
- 장 제목 문단으로 장을 나눈다. **문서를 다른 사람이 다시 저장하면 제목 스타일 id가 바뀔 수 있다(예: 「1」 → 「Heading1」).** 두 가지 모두 받고, 작업 전에 Ⅰ~Ⅸ장이 모두 잡혔는지 확인(없으면 멈춤)한다. 장 구분이 틀리면 「다른 장은 건드리지 않는다」는 규칙이 무너진다.
- 장 제목 줄이 빠진 판(예: 「Ⅰ. 회사의 개황」 없이 「1. 상장을 계획한 시기」부터 시작)도 있으니 대체 기준을 둔다.

## 7. 두 문서 합치기(작업본을 공유본 위에 덮기)
공유 드라이브본(다른 팀 장 포함)에 우리 작업 장만 덮어써야 할 때:
1. 공유본을 바탕으로 둔다(스타일, 번호, 머리말, 바닥글, 다른 팀 장, 그림, 메모 유지).
2. 우리가 맡은 장 구간만 작업본 내용으로 바꾼다.
3. 메모 번호가 겹치지 않게 새 번호를 매기고 부속 메모 파일도 함께 옮긴다. 바꾼 구간에 있던 공유본 메모는 뺀다(작업본에서 정리된 것으로 대체).
4. 그림은 공유본에 새로 넣고 연결 번호(rId)를 다시 붙인다.
5. **기본 줄간격 등 문서 기본값이 두 파일에서 다르면** 옮긴 문단에 원래 값을 직접 지정해 모양을 유지한다(공유본 기본값은 바꾸지 않음).
6. 검증: 바꾼 장은 작업본과 글이 같고, 남긴 장은 공유본과 XML까지 같으며, 메모 수 = 남긴 장 메모 + 옮긴 메모, 그림 수, 마지막 구역 설정이 같은지.
7. 공유본이 작업본보다 오래된 판인지(@ 반영 전) 먼저 확인한다. 공유본에만 있는 새 내용이 있으면 사용자에게 알린다.
8. **사용자가 내려받아 준 공유 작업본이 기준이다.** 회사, 사용자가 직접 고치고 메모를 단 판이므로, 내 판을 기준으로 삼지 않고 그 위에 우리 장만 덮는다.
9. 공유본의 메모는 이렇게 다룬다: 새 메모(이전 판에도, 내 판에도 없는 것)는 같은 표(머리행, 순번으로 찾음)의 같은 칸에 옮긴다. 회사가 글만 고친 메모는 기존 메모의 글을 바꾸고 답글은 유지한다. 공유본에서 지운 메모는 지운다.
10. 웹 편집기로 저장된 공유본은 스타일 id가 바뀐다(예: 「1」→「Heading1」, 메모 참조 스타일 이름 변경). 스타일은 id가 아니라 이름으로 대응시키고, 마지막에 「없는 스타일을 가리키는 문단 0」을 확인한다.

### 7-1. 판 만드는 순서(판이 꼬이지 않게)
1. 우리 장에 회신 자료와 회사 파일에서 확인되는 정보를 먼저 반영한다.
2. 그 결과를 사용자의 최신 작업본(공유 드라이브에 올라간 판) 위에 장 단위로 덮는다. 다른 팀 장과 표지는 최신본 XML 그대로 두고, 매번 서식, 그림, 메모까지 XML이 같은지 검증해 보고한다.
3. 사용자 작업본 대비 차이 전부를 비교 파일로 만든다(9-1절).

## 8. 검증 방법(판마다)
- **칸 단위 전후 비교:** 바꾼 칸과 문단마다 「전」과 「후」 글을 출력해 의도한 것만 바뀌었는지 눈으로 본다. 줄 집합 비교만으로는 칸 안 중복 글자 같은 오류를 놓친다.
- 다른 장: XML 동일.
- 메모 수와 본문 연결(연결 없는 메모 0, 없는 메모를 가리키는 표시 0).
- 그림 수, 형광펜, 글자색 변화(장별로 「사라진 색 / 새 색」 목록).
- 남은 @ 0건.
- 숫자를 바꿨다면 합계, 소계가 맞는지(예: 항목을 다른 연도로 옮기면 연도별 소계도 바뀐다).
- **표 행이나 문단을 복제하면 문단 id(`w14:paraId`)가 겹친다.** 칸을 지우고 다시 쓰면 그 안의 메모 표시가 떨어진다. 고친 뒤 항상 「메모 수 = 참조 수」, 「겹친 paraId 0」을 확인하고, 떨어진 메모는 바뀐 자리에 다시 붙인다.
- 새로 만든 표에 표 설정(테두리, 폭)이 있는지, 빈 문단으로 띄운 곳이 없는지(03 문서 규칙 33, 34).

## 8-1. 외부 리뷰 메모를 한꺼번에 반영할 때(주관사, 회계법인, 회사)
리뷰 메모가 수십 건 오면 대부분이 「양식 표와 일치시켜 달라」는 서식 지적이다. 여러 장을 동시에 손으로 고치면 장끼리 숫자, 서술이 어긋난다(Ⅰ장과 Ⅶ장 최대주주 변동표, 위원회 서술이 서로 다르게 고쳐지는 식). 그래서 「명세 → 한 스크립트 → 검증」으로 한다.
1. **명세:** 메모를 영역별로 나누고, 분석 담당은 정해진 형식의 명세 파일(json)만 쓴다. 메모마다 대상 위치, 바꿀 내용, 근거를 적는다.
2. **반영:** 반영 스크립트는 하나다. 대상은 손대기 전 원본에서 미리 찾고, 삭제를 먼저 한 뒤 넣는다. 양식 표를 가져올 때는 양식 docx의 머리행과 병합을 그대로 복사한다. 리뷰어 메모는 지우지 않고 새 표에 다시 붙인다.
3. **검증:** 장별 XML(다른 장 불변), 메모 연결, 새로 생긴 숫자, 양식 머리행 일치, 문체를 검사하고, 반영에 끼지 않은 검토자 둘(리뷰어 시각)에게 다시 보게 한다. 지적이 나오면 결과물을 고치지 말고 명세를 고쳐 원본부터 다시 만든다.
4. **판단이 걸린 사실**(예: 의결권 기준 최대주주 판정)은 한 장에만 쓰지 말고 문서에서 빼 두고 의사결정 목록으로 올린다. 사용자가 직접 고친 값은 원장 근거가 달라도 바꾸지 않고 주석으로 맞춘다.
5. 외부의견 반영표, 회신 초안, 자료요청 추가분(번호 이어서), 자료요청 전체 리스트 줄 추가까지 한 번에 낸다.
6. **회신 표기:** 「[반영] / [부분반영] / [미반영] / [확인 중] / [확인 요청]」 뒤에 사실만 쓴다. 사용자 결정을 기다리는 항목에는 답글을 달지 않는다.
7. **다른 판에 단 메모 옮겨 달기:** 리뷰어가 우리 판이 아닌 다른 판(예: 오전 공유본)에 메모를 달았으면, 절 제목 문단을 찾고 그 아래 문맥 → 메모 범위 글 순서로 맞는 첫 문단에 단다. 같은 키를 「차례로」 배정하면 엉뚱한 자리로 밀린다. 다른 팀 장과 표지에 단 메모는 그 장 XML을 바꾸지 않으려고 옮기지 않고 반영표에만 적는다.

## 8-2. 외부에 주는 파일에 내부 표현을 남기지 않는다
루트의 신청서와 비교 파일은 모두 주관사, 회사에 가는 파일이다.
- 책임자 호칭(「대표님」 등), 「사용자 지시」, 「우리 장」, 「덮은 판」, 내부 파일명, AI 도구 이름(클로드, 코덱스 등)을 넣지 않는다. 판 이름은 「기존 작업본」, 「반영본」처럼 중립으로 쓴다. 리뷰어 메모를 인용할 때도 호칭은 직함으로 바꾼다.
- 원천 서류를 고쳐 받았다는 표현(「소급」, 「수정된 의사록」, 「수정본」)과 타사명은 본문뿐 아니라 메모, 답글, 안내 줄까지 `word/*.xml` 전체를 검사해 0건으로 만든다.
- python-docx로 만든 파일은 문서 속성(작성자 「python-docx」, 설명 「generated by python-docx」)이 남으니 비운다.

## 9. 보고
- 바꾼 것(근거: 요청 번호, 메모), 그대로 둔 것, 사용자가 판단할 것(근거가 간접적인 값, 이상한 날짜, 한 달 겹치는 경력 등)을 나눠 쓴다.
- 실수했으면 무엇이 틀렸고 어떻게 고쳤는지, 원본은 무사한지 먼저 말한다.

### 9-1. 전후비교 파일(리뷰 반영 결과를 보여 줄 때)
- A3 가로. 변경 건마다 틀 표 하나: 윗줄은 거래소 양식 표(참고, 양식 표 번호와 제목), 아랫줄은 왼쪽 변경 전 | 오른쪽 변경 후(위 정렬). 사용자가 줄끼리 옆으로 비교한다.
- 단위는 「주제별」이다. 바뀐 자리의 절(바로 다음 제목까지) 전체를 반영 전 | 반영 후로 보인다. 절은 합치지 않고 하나씩(가., 나. 따로) 두고, 메모 없이 문구만 맞춘 절은 부록으로 뺀다. 사용자가 맡지 않은 표지 등은 넣지 않는다.
- 바뀐 곳 표시: 지운 글은 빨간 취소선, 새로 넣은 글은 파란 밑줄, 고친 문단은 낱말 단위, 옮긴 문단은 주황, 표는 바뀐 칸 음영.
- 변경 전은 작업 전 보관본에서, 변경 후는 최종 신청서에서 글 유사도로 찾아 가져온다(반영 뒤 서식 정리가 쌓여도 어긋나지 않는다). 마지막에 전, 후 각각 원본 글과 0건 차이인지 전수 대조한다.
- 리뷰 메모, 구두 협의, 회사 자료로 바뀐 절은 본문에, 제출 전 점검으로 우리가 스스로 고친 숫자, 용어, 문장과 회사 수정을 받아들이지 않은 곳은 맨 뒤 「내부 확인용」에 둔다. 외부용은 내부 확인용을 뺀 판을 따로 만든다. 우리 쪽 임의 수정이 외부에 보이지 않게 하기 위해서다.

## 10. 점검표
- [ ] 시작점이 사용자, 회사가 마지막으로 고친 docx다
- [ ] 받은 파일을 보관했고 보관본에서 읽었다
- [ ] 장 구분이 Ⅰ~Ⅸ 모두 잡혔다
- [ ] @ 0건, 지시 문구 잔여 없음
- [ ] 다른 팀 장 XML 동일, 그 장 메모 그대로
- [ ] 바꾼 칸을 하나하나 전후 대조했다
- [ ] 연결 없는 메모 0
- [ ] 색 처리가 사용자 기준과 맞다
- [ ] 기록 두 개(검토기록, 폴더변경기록)를 남겼다
- [ ] 고치기 전 잠금 파일을 확인했고, 고친 뒤 사용자 저장 여부(core.xml)를 확인했다
- [ ] 메모 수 = 참조 수, 겹친 paraId 0, 없는 스타일 참조 0
- [ ] 외부 전달 파일에 호칭, 내부 표현, 타사명, 원천 수정 표현이 0건(xml 전체)
