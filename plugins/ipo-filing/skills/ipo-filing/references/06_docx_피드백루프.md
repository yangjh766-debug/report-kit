# 06. docx 피드백 루프 (사용자, 회사가 docx를 직접 고치기 시작한 뒤)

신청서 docx를 사용자와 회사가 직접 고치기 시작하면, 그 docx가 원본이 된다. 이 문서는 그 뒤에 판을 거듭하는 방법이다. 핵심은 **지시받은 곳만 고치고 나머지는 한 글자도 바꾸지 않는 것**이다.

---

## 1. 판 하나를 만드는 순서

```mermaid
flowchart TD
    A[사용자, 회사가 고친 docx 받음] --> B[날짜 붙여 이력 폴더에 보관]
    B --> C[이전 판과 비교<br/>장별 바뀐 줄, 새 메모, @ 지시]
    C --> D[@ 지시, 회신, 메모를 할 일 목록으로]
    D --> E[고칠 것만 고치는 스크립트 또는 수작업<br/>원본은 보관본에서 읽음]
    E --> F[칸 단위 전후 대조<br/>다른 장 XML 동일, 메모 수, 색]
    F -->|의도 밖 변화| E
    F --> G[다음 판 저장 vDraft-N+1]
    G --> H[기록: 검토기록, 폴더변경기록]
    H --> I[사용자에게 보고<br/>바꾼 것, 남긴 것, 확인 필요]
```

```
[고친 docx 받음] → [보관] → [이전 판과 비교] → [할 일 목록]
   → [고칠 곳만 수정] → [칸 단위 대조] ─(의도 밖 변화)→ 다시 수정
   → [다음 판 저장] → [기록] → [보고]
```

## 2. 받은 파일 다루기
1. **시작점은 항상 사용자가 마지막으로 고친 docx.** md에서 다시 만들지 않는다(사용자가 지운 것이 되살아나고, 고친 서식이 사라진다).
2. 받은 파일은 곧바로 `검토/docx_이력/<무엇>_<누가>_<MMDD_HHMM>.docx`로 복사해 두고, 스크립트는 이 보관본을 읽는다. 사용자가 Word로 열어 둔 파일을 직접 고치지 않는다.
3. 결과는 새 이름으로 저장한다(vDraft-N → vDraft-N+1). 사용자가 쓰는 이름 체계가 있으면 따른다.
4. 파일 수정 시각을 보고 사용자가 그 사이 고쳤는지 확인한다. 고쳤으면 그 판을 새 시작점으로 삼는다.
5. Word 잠금 파일(`~$…`)이 있으면 열려 있는 것이다. 덮어쓰지 않는다.

## 3. @ 지시 처리
- 사용자는 본문이나 표 칸에 「@지시」를 적는다. 지시를 수행하고 @ 문구는 지운다.
- **@ 문구가 두 문단 이상에 걸칠 수 있다.** @부터 그 칸(또는 문단 묶음) 끝까지 지우고, 지운 뒤 「@」가 0건인지, 지시 문구의 뒷부분이 남지 않았는지 확인한다.
- 지시가 모호하면 사용자가 직접 고친 예시를 본다. 예: 한 칸을 직접 두 줄로 나누고 「@이런식」이라고 쓰면, 같은 표의 비슷한 칸도 그렇게 하라는 뜻이다.
- 지시가 「여기는」이라도 같은 구조의 표가 여러 개면(예: 연도별 임원 표) 같이 맞추고 그렇게 했다고 보고한다.
- 「요청자료에 있나?」 같은 질문형 @는 요청 리스트를 확인해 답하고, 없으면 요청 한 줄을 추가한다.

## 4. 사용자, 회사 수정의 보존
- 사용자가 지운 것, 줄인 것, 직접 고친 문구는 그대로 둔다.
- **색 표시:** 회사는 새 입력에 빨간 글자나 빨강, 노랑 형광펜을 칠해 두는 경우가 많다. 기본은 그대로 두되, 사용자가 원하지 않으면 다음처럼 정리한다(작업 전에 한 번 확인).
  - 형광펜은 모두 빼고, 채워야 할 대기 표식(`##`, `[확인 필요: …]`, `[작성 대기: …]`)만 노란색.
  - 회사 입력의 빨간 글자는 검은색. 단, 안내 메모(「확인 필요」 같은 지시문, 주관사 몫 안내)는 색을 남겨 본문과 구분.
  - 회사 입력 글을 다시 쓸 때(줄바꿈 정리 등) 첫 글자의 서식을 복사하면 회사의 빨간색이 따라온다. 의도와 맞는지 확인한다.
- **다른 팀이 맡은 장**(예: 사업의 내용)은 내용, 서식, 메모, 색까지 손대지 않는다. 결과에서 그 장이 원본과 XML 단위로 같은지 확인한다.
- 문서 전체에 서식 스크립트(정렬, 줄간격, 글자 크기)를 돌리지 않는다. 고친 표나 문단에만 적용한다.

## 5. 메모(Word 메모)
- 「완료」, 「기입 완료」, 「수정했습니다」 같은 회신 메모는 내용을 확인한 뒤 지운다.
- 질문, 확인 요청(「확인 부탁드립니다」), 아직 답하지 않은 것은 남긴다.
- 우리가 다는 메모는 사용자 판단이 필요한 곳에만 한다. 예: 문서 원문과 다르게 적은 곳의 근거와 확인 요청. 메모 내용은 요청 리스트에도 한 줄로 남긴다(메모를 지워도 놓치지 않게).
- 메모를 지울 때는 본문의 시작, 끝 표시, 참조 런, 메모 본체와 부속 파일(commentsExtended, commentsIds, commentsExtensible)을 함께 지운다. 문단을 지우거나 합치면 그 안의 메모 표시도 사라지므로, 마지막에 **본문에 연결이 없는 메모가 남지 않았는지** 확인한다.
- 다른 팀 장의 메모는 지우지 않는다.

## 6. 장 구분
- 장 제목 문단으로 장을 나눈다. **문서를 다른 사람이 다시 저장하면 제목 스타일 id가 바뀔 수 있다(예: 「1」 → 「Heading1」).** 두 가지 모두 받고, 작업 전에 Ⅰ~Ⅸ장이 모두 잡혔는지 확인(없으면 멈춤)한다. 장 구분이 틀리면 「다른 장은 건드리지 않는다」는 규칙이 무너진다.
- 장 제목 줄이 빠진 판(예: 「Ⅰ. 회사의 개황」 없이 「1. 상장을 계획한 시기」부터 시작)도 있으니 대체 기준을 둔다.

## 7. 두 문서 합치기(작업본을 공유본 위에 덮기)
공유 드라이브본(다른 팀 장 포함)에 우리 작업 장만 덮어써야 할 때:
1. 공유본을 바탕으로 둔다(스타일, 번호, 머리말, 바닥글, 다른 팀 장, 그림, 메모 유지).
2. 우리가 맡은 장 구간만 작업본 내용으로 바꾼다.
3. 메모 번호가 겹치지 않게 새 번호를 매기고 부속 메모 파일도 함께 옮긴다. 바꾼 구간에 있던 공유본 메모는 뺀다(작업본에서 정리된 것으로 대체).
4. 그림은 공유본에 새로 넣고 연결 번호(rId)를 다시 붙인다.
5. **기본 줄간격 등 문서 기본값이 두 파일에서 다르면** 옮긴 문단에 원래 값을 직접 지정해 모양을 유지한다(공유본 기본값은 바꾸지 않음).
6. 검증: 바꾼 장은 작업본과 글이 같고, 남긴 장은 공유본과 XML까지 같으며, 메모 수 = 남긴 장 메모 + 옮긴 메모, 그림 수, 마지막 구역 설정이 같은지.
7. 공유본이 작업본보다 오래된 판인지(@ 반영 전) 먼저 확인한다. 공유본에만 있는 새 내용이 있으면 사용자에게 알린다.

## 8. 검증 방법(판마다)
- **칸 단위 전후 비교:** 바꾼 칸과 문단마다 「전」과 「후」 글을 출력해 의도한 것만 바뀌었는지 눈으로 본다. 줄 집합 비교만으로는 칸 안 중복 글자 같은 오류를 놓친다.
- 다른 장: XML 동일.
- 메모 수와 본문 연결(연결 없는 메모 0, 없는 메모를 가리키는 표시 0).
- 그림 수, 형광펜, 글자색 변화(장별로 「사라진 색 / 새 색」 목록).
- 남은 @ 0건.
- 숫자를 바꿨다면 합계, 소계가 맞는지(예: 항목을 다른 연도로 옮기면 연도별 소계도 바뀐다).

## 9. 보고
- 바꾼 것(근거: 요청 번호, 메모), 그대로 둔 것, 사용자가 판단할 것(근거가 간접적인 값, 이상한 날짜, 한 달 겹치는 경력 등)을 나눠 쓴다.
- 실수했으면 무엇이 틀렸고 어떻게 고쳤는지, 원본은 무사한지 먼저 말한다.

## 10. 점검표
- [ ] 시작점이 사용자, 회사가 마지막으로 고친 docx다
- [ ] 받은 파일을 보관했고 보관본에서 읽었다
- [ ] 장 구분이 Ⅰ~Ⅸ 모두 잡혔다
- [ ] @ 0건, 지시 문구 잔여 없음
- [ ] 다른 팀 장 XML 동일, 그 장 메모 그대로
- [ ] 바꾼 칸을 하나하나 전후 대조했다
- [ ] 연결 없는 메모 0
- [ ] 색 처리가 사용자 기준과 맞다
- [ ] 기록 두 개(검토기록, 폴더변경기록)를 남겼다
